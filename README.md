# mts-mlops-hw3

Сервис скоринга фродовых транзакций из ДЗ №1–2 с оркестрацией переобучения в
Apache Airflow. Сервис читает транзакции из Kafka, считает скор моделью из
общего каталога и складывает результат в Postgres. Airflow по расписанию
переобучает модель на скользящем окне, публикует новую версию в тот же каталог
и проверяет датасет на требования Data Quality.

## Состав

| Сервис | Что делает | Порт на хосте |
| --- | --- | --- |
| `fraud_detector` | читает `transactions`, публикует результат в `scores` | — |
| `scoring_writer` | пишет результаты скоринга в таблицу `scores` | — |
| `transaction_simulator` | шлёт строки `train.csv` в `transactions` с новым id и текущим временем | — |
| `airflow` | UI и планировщик трёх DAG | 8081 |
| `postgres` | витрина `labeled_transactions`, состояние окна и таблица `scores` | 5432 |
| `kafka`, `zookeeper` | брокер сообщений | 9092 |
| `kafka-ui` | просмотр топиков | 8080 |
| `data_loader` | разовая инициализация: витрина, окно обучения, стартовая модель | — |

## Быстрый старт

## Быстрый старт

Окружение: Linux, macOS или Windows с Docker Desktop, либо WSL2. Нужны Docker
с плагином `docker compose` и размеченный CSV из ДЗ №1 (датасет `teta-ml-1`,
786 431 строка). Больше ничего ставить не нужно: Airflow, CatBoost, Kafka и
Postgres поднимаются в контейнерах.

```bash
cp .env.example .env
# пропишите в .env путь к train.csv так, как его видит ваш демон Docker
docker compose up --build -d
```

Путь к CSV в `.env` отличается в зависимости от платформы:

| Окружение | Формат `TRAIN_DATA_CSV` |
| --- | --- |
| Linux, macOS | `/home/<user>/datasets/train.csv` |
| Docker Desktop на Windows | `C:/Users/<user>/datasets/train.csv` |
| Docker внутри WSL2 | `/mnt/c/Users/<user>/datasets/train.csv` |

Если демон Docker запущен внутри WSL2, Windows-путь вида `C:/...` он не
примет: нужна форма `/mnt/c/...`. Это единственное место, где платформа влияет
на запуск.

Порядок запуска обеспечивают зависимости в compose: `data_loader` ждёт
Postgres, затем загружает витрину, ставит начальное окно, готовит
`training_data/current.parquet` и обучает стартовую модель, после чего
запускаются Airflow и сервис скоринга. Загрузка CSV и обучение занимают
примерно минуту-полторы, до этого Airflow ещё не поднят: это нормально.

Проверить, что стартовая модель появилась:

```bash
ls models/
# latest.txt  metrics_initial.json  model_initial.cbm  preproc_initial.json
```

## Airflow

UI: http://localhost:8081, пользователь `admin`, пароль `admin`.

Все три DAG включены при создании и запускаются по расписанию раз в 5 минут
(`catchup=False`). Их можно запускать и вручную кнопкой **Trigger DAG**.

| DAG | Что делает |
| --- | --- |
| `retrain_catboost` | скользящее окно, обучение, проверка улучшения, публикация версии |
| `supply_labeled_batch` | дописывает в витрину следующий месяц и чистит старое |
| `check_dataset_quality` | проверки датасета и HTML-отчёт |

### Как убедиться, что работает

1. **Поставка.** Запустите `supply_labeled_batch`. В логе задачи
   `sample_next_month` виден целевой месяц, в `append_labeled_batch` — число
   дописанных строк. Повторный запуск помечает задачу `skipped`: месяц уже в
   витрине, дублей нет.
2. **Переобучение.** Запустите `retrain_catboost`. Задача `extract_month_batch`
   берёт месяц из указателя, `slide_training_window` выбрасывает самый старый
   месяц окна, `fit_catboost` обучает кандидата, `publish_model` публикует его.
3. **Новая версия в каталоге моделей.** В общем каталоге появляются
   `model_<версия>.cbm`, `preproc_<версия>.json` и `metrics_<версия>.json`,
   а `latest.txt` указывает на новую версию:

   ```bash
   cat models/latest.txt
   ```

4. **Сервис скоринга подхватил версию.** Перезапуск не нужен: указатель
   читается на каждом сообщении. В логах `fraud_detector` строка
   `Активна версия модели <версия>`.
5. **Версия видна в результате скоринга.** В таблице `scores` есть колонка
   `model_version`:

   ```bash
   docker compose exec postgres psql -U fraud_user -d fraud_db -c \
     "select model_version, count(*), max(created_at) from scores group by 1 order by 3 desc;"
   ```

   Топ же результат можно посмотреть в Kafka UI: топик `scores`.

6. **Отчёт Data Quality.** Запустите `check_dataset_quality`, затем откройте
   свежий файл:

   ```bash
   ls dq_reports/
   ```

## Окно обучения и данные

- Глубина истории витрины — **1 год** (`HISTORY_YEARS = 1`), по умолчанию в
  семинаре было 3 года. Уменьшено, чтобы чистку старых наблюдений было видно
  за разумное число прогонов поставки.
- Размер батча поставки — **100 000 строк** (`SAMPLE_SIZE`).
- Окно обучения — **3 месяца** (`WINDOW_MONTHS`): при поставке нового месяца
  в окно добавляется он, а самый старый месяц убирается.
- Разбиение train/test — по времени: ранние месяцы окна идут в обучение,
  самый свежий месяц — в проверку.
- Препроцессинг — собственная схема, чуть более занятные фичи: логарифм суммы,
  отношение суммы к медиане мерчанта, час суток и его синус/косинус, день
  недели, признаки ночи и выходного, регион по первой цифре ZIP, плюс
  категориальные признаки для CatBoost. 
- Медианы суммы по мерчантам считаются только по обучающей части окна и
  публикуются рядом с моделью (`preproc_<версия>.json`), поэтому расхождения
  между обучением и скорингом нет.

## Проверка улучшения модели

Перед публикацией версия сравнивается с активной. Метрика сравнения — ROC-AUC
на своём проверочном месяце (самый свежий месяц окна, для обеих версий это
первый месяц условного «будущего»).

- Если ROC-AUC кандидата не хуже ROC-AUC активной версии с учётом допуска
  `METRIC_TOLERANCE = 0.005`, версия публикуется.
- Если хуже — задача `evaluate_against_current` помечается `skipped`,
  публикация и сдвиг указателя месяца не выполняются, активной остаётся
  предыдущая версия. Артефакты кандидата остаются на диске для разбора.
- Люфт небольшой нужен, так как метрика может быть немного шумной в третьем знаке.

В каталоге моделей остаются текущая и предыдущая пары — этого достаточно для
отката без повторного обучения. Лишние пары и модели без словаря удаляются при
очередной публикации.

## Правила Data Quality

`check_dataset_quality` проверяет текущее окно обучения. Референс известных
значений — более ранние месяцы того же окна, поэтому новые мерчанты и
категории видны как отклонение. Отчёт по каждому правилу печатается в
`dq_reports/`; провал правил не валит задачу, статус виден в отчёте. Для
городов и ZIP порог задан долей строк, потому что новые значения там
появляются естественно: по замерам на датасете новых городов 0.10 %, новых
ZIP 0.13 % строк.

| Правило | Порог |
| --- | --- |
| обязательные колонки присутствуют | все 5 обязательных |
| доля пропусков в обязательных колонках | 0 |
| отметки времени внутри периода наблюдений | 0 наблюдений вне |
| метка принимает только 0 и 1 | только 0 и 1 |
| доля фрода | 0.05 % … 5 % |
| сумма транзакции строго положительна | 0 неположительных |
| доля дублей по время+мерчант+сумма | ≤ 0.1 % |
| новые значения признаков с малым числом значений (`cat_id`, `gender`, `us_state`) | 0 новых значений |
| доля строк с новым значением для `merch`, `jobs`, `one_city`, `post_code` | ≤ 5 % |
| доля строк с новыми мерчантами | ≤ 5 % |

## Структура

```
dags/                 сборка графов, логика в pipeline/
pipeline/             общая схема признаков, обучение, витрина, проверки
pipeline/retrain/     задачи DAG переобучения
pipeline/supply/      задачи DAG поставки
pipeline/quality/     правила Data Quality и HTML-отчёт
fraud_detector/       сервис скоринга и горячая подмена версии модели
scoring_writer/       результаты скоринга в Postgres
transaction_simulator/ поток транзакций в Kafka
data_loader/          стартовая инициализация стенда
airflow/              образ Airflow с CatBoost
postgres/init/        схема таблиц
models/               общий каталог версий модели
dq_reports/           HTML-отчёты Data Quality
scripts/              вспомогательные скрипты для тестирования (в рантайме не нужны)
```

### Вспомогательные скрипты

Каталог `scripts/` в работе сервисов не участвует: это проверки, которыми
разрабатывался и проверялся пайплайн. Запускать их не обязательно.

| Скрипт | Что проверяет |
| --- | --- |
| `check_features.py` | признаки на реальном CSV: доли фрода по сегментам, полнота словаря медиан |
| `check_scoring_contract.py` | путь сообщения из Kafka через признаки до матрицы для модели |
| `check_pipeline_integration.py` | витрина, поставка и переобучение на живом Postgres |
| `check_dags.py` | что все три DAG собираются и задачи связаны в ожидаемый граф |
| `train_initial.py` | обучение стартовой модели отдельно от стека |
| `probe_early_stopping.py` | подбор терпения early stopping на первом окне |

Путь к CSV скрипты берут аргументом или из переменной окружения `TRAIN_DATA_CSV`,
например: `python scripts/check_features.py /data/train.csv`.
